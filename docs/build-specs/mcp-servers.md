# Build spec: the two MCP servers (Phase 4)

What exists at the end: `mcp/records_server.py` (`MCP_RECORDS_PORT`, 8831; the proofs 8304) answers every records tool of
`docs/consultant-tracking-mcp-tool-surface.md` — the people, vocabulary and rates; clients and engagements; time; expenses; AI usage and hosting;
billing and the reports; the six `shares[]`; `app_roles`; `records_search` — and `mcp/activity_server.py` (`MCP_ACTIVITY_PORT`, 8832; the proofs 8305) answers the
activity tools over `mcp_activity_log`. Both read as the connected read role (`consultant_tracking_records_ro` / `consultant_tracking_activity_ro`) with
`app.member_id` set transaction-locally from the verified bearer: **the views and the `ct_*` report functions decide who sees what, the server only
trims** (it never fills a column a view blanked). Nothing here writes — the action tools are the kernel's Actions MCP, built from `mcp/action_registry.json`
through `deploy/kernel-registry-consultant_tracking.json`.
Schema: nothing new (db/001–018 stay as they are). Screens: none.

## Who gets in (`mcp/server_common.py`, copied from General Ledger/Help Desk and widened by the six shares)
- A person: their own `mcp_` token (`mcp_resolve_token(hash, 'mcp')`), or the command bar's action token (`mid.exp.hmac`, ACTION_TOKEN_KEY) for a member the mirror knows and admits — every tool, scoped by the views.
- An agent: the tenant's signed RUN token (`mid.exp.run.hmac`); the server asks the kernel's `/api/v1/runs/facts.php` once per run (cached five minutes) with the application's token and offers EXACTLY the tools the kernel names for this endpoint ("Records MCP" / "Activity MCP"). Facts that say invalid, another application's, no endpoint here, or a kernel that cannot be reached: nothing is offered (fail closed). An agent the directory has not admitted is admitted at first contact only when the kernel vouches for it with endpoints here (`mcp_admit_agent`).
- The kernel's own 60-second token (`kernel.exp.app.nonce.hmac`): `app_roles` and the six shares, nothing else (403 in words). It sends a share's arguments flat; the server wraps them.
- `X-Eval-Run`: every tool is read-only; nothing is marked. An eval run's facts (`is_eval`) are honoured like any agent's.

## How the shares reach slice 8's functions (one truth, two doors)
The six share tools (`invoices_issued`, `credit_notes_issued`, `expenses_by_category`, `unbilled_summary`, `reimbursements_approved`, `engagement_list`) do NOT reimplement the documents. They POST to
the application's own internal port — `POST /api/v1/shares/read.php` on `APP_INTERNAL_PORT` (loopback; the public vhost blocks `/api`) — which calls the very functions in `app/features/exports/documents.php`
(`share_invoices_issued` …) that the exports page and its downloads call, as `caller = 'kernel'` (the firm's administrator for the length of the call, `share.read` logged by the function) or `caller = 'person'`
(`app.member_id` = the verified member; the function's own right check, `ShareRefused` → the tool's words). The request is authenticated by an HMAC over `share:<unix time>:<sha256 of the body>` with `ACTIONS_RELAY_KEY` (the
key the agent never holds; ±120 s). The tool answers the document unchanged, `rows` and all. A refusal is a tool error in the function's sentence.
The two cases that are not shares at all — a `q` alone on `credit_notes_issued` (the resolver's plain list) — read the `mcp_credit_notes` view directly.

## Decisions taken while building
- **The shares reach slice 8's functions over the application's own internal door**, `POST /api/v1/shares/read.php` (HMAC over `share:<time>:<sha256 of the body>` with `ACTIONS_RELAY_KEY`, ±120 s, loopback only — the public vhost answers 404 for `/api`). The tool answers the document's own JSON text unchanged (key order and money strings as built). One truth, two doors, and `share.read` is written by the PHP function (the read role cannot write the log). A person's or an agent's read through the tool is not logged as `share.read` (the function logs the kernel's calls only; a person's download is the exports page's).
- **A refusal is a tool error**, in the function's own sentence (MCP `isError`), not an HTTP 403 — as Help Desk's and Projects' servers do; the kernel reports it to the consumer as `provider_failed`.
- **The surface's "43 named tools" was a miscount: the tables name 46** (plus `records_search` and `app_roles` = 48). No tool was added or dropped; the surface's Size line is corrected.
- **`unbilled_items` is gated like `unbilled_summary`** (invoices.draft, reports.view or billing.write) — tighter than the surface's "staffed", because it carries bill value (slice 8's rule for the summary).
- **The `ct_settings` resolver**: one tool resolves four entities with four id fields, and the kernel calls it with `q` alone — so `q` alone answers a flat list of the roles, activity types, categories and providers that match, each row carrying ITS OWN id field (`consulting_role_id`, `activity_type_id`, `category_id`, `provider_id`) and label; the kernel's filter on `id_field` then picks the entity it wants.
- **`my_timesheet` and `my_expenses` with `q` alone resolve what the view admits, the caller's own first**, a team member's labelled "<person> — …" (a superset of the surface's "of the caller's"): without it an approver could not approve an expense or write off an entry BY NAME through the kernel's resolver. The views still decide who is seen.
- **Costs stay masked**: `budget_status`, `get_engagement`, `budget_alerts` null the AI cost, its percentage and the budget's alert values (and show the AI budget as "set") unless the caller has `cost.view` on that engagement or `usage.write`; `ai_passthrough` nulls cost and markup without `cost.view` or `usage.write` — as the screens do. `margin` answers only after `cost.view` and only through `ct_margin()`.
- **What the records role cannot read is not faked**: no last-events list on `get_engagement` / `get_invoice` and no secure-link state on `get_invoice` (`activity_log` and the link table are not granted — `record_history` is the answer), no numbering prefixes on `ct_settings`.
- **`maludb-os.json` gained the two MCP endpoints** ("Records MCP" `/mcp/records` on `MCP_RECORDS_PORT`, "Activity MCP" `/mcp/activity` on `MCP_ACTIVITY_PORT`, bearer, agent-reachable, surface 1.0) that Phase 0 left out — the run-facts call names its endpoints by these, and the installer registers them and finds the records URL from them.
- **Six manifest rows had commas inside a hint** (`settings_save`, `milestone_delete`, `timer_stop`, `timesheet_reopen`, `time_entry_write_off`, `secure_link_rotate`), which the registry builder turns into phantom parameters — so on the kernel's Actions MCP those tools would have lost their real fields (`entry`, `milestone`, `timesheet`, `invoice`, the settings' fields). The rows now follow the manifest's own rule; the registry was rebuilt (108 of 108 built, nothing else moved); `registry.php` asserts no phantom remains.
- **The resolve wrapper is kept by hand** (it cannot be derived from the registry); `accepted_by` and `morning_note_member` were added to the `member` entity. No `bin/build_kernel_registry.php` was written; `registry.php` proves the wrapper against the kernel's own loader instead.
- Money in tool answers is a JSON number (the database's `numeric` as a float, two decimals in practice); the six documents keep their strings. Times are UTC with a `_local` twin in the caller's zone where a timestamp is the point. `actor_timeline` returns every row (sign-ons and views included); `record_history`, `who_touched` and `recent_activity` leave `screen.view` out.
- `X-Eval-Run` and an eval run's facts are accepted and change nothing: every tool reads.

## Open questions
- **Last events and the secure link on `get_engagement` / `get_invoice`.** The surface lists them; the read roles are not granted `activity_log` or the link table, and widening a grant needs a migration with the owner's sign-off. Today the expert answers "what happened to this invoice" with `record_history` and never sees whether a link is live, rotated or expired. A view over the link's state (never the token) granted to the records role would close it.
- **`share_reads` cannot say which sibling read.** The kernel calls a share with its own anonymous token (K7), so the inbound `share.read` row names the tool and the keys but no application; the `app` filter matches only our outbound reads (`gl`, `hr`). Should the kernel send the consumer's key (a header the door could log)?
- **The numbering prefixes** (`INV-`, `CN-`, `EXP-`…) are in `document_sequences`, which no view exposes; `ct_settings` leaves them out. Worth a view, or leave to the screen?
- **`usage_charge` resolves among DRAFTS only** (`usage_pending`, as the surface says), so `usage_charge_void` by name cannot find an approved charge — the id works. Widen the resolver to every non-void charge the view admits?
- **A person's read of a share is not logged as `share.read`** (only the kernel's is, per slice 8); Billing's own reads leave no trace but the exports page's `export.download`. Intended?
